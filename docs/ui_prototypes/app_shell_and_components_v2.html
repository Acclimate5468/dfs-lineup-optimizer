Porting this into Streamlit

This v2 prototype is a view-layer exploration. Everything maps to data the app already computes; no new business logic, schema, or page-load writes are implied.

1. The shell (biggest usability win, lowest logic risk)

  • Persistent context bar (slate chip + gate pill + readiness mini): render once via a tiny helper imported at the top of each page, fed by evaluate_manual_review(conn, st.session_state["active_slate_id"]). Streamlit's native sidebar already gives the left nav; the status dots beside each page would be a small bonus (one readiness read shared via st.session_state or a cached call).
  • Page header pattern: a shared render_page_header(title, subtitle, banner) helper so every page opens with breadcrumb ▸ title ▸ purpose ▸ contextual banner ▸ next-step hint. Today each page rolls its own intro.

2. Components → Streamlit primitives

  • Banners → st.success / st.warning / st.error / st.info (native) or the small CSS banner if a richer look is wanted.
  • Status cards → st.columns + st.container(border=True) + st.metric + a CSS status chip.
  • Status tables → the existing dataframes gain a status column; for per-row action buttons keep the column-of-st.columns pattern already used by the Fight Groups fight-card table and the Odds review queue.
  • Stepper → a row of small st.columns with an icon per step (pure markdown).
  • One shared CSS block injected once per page via st.markdown(unsafe_allow_html=True) (scoped llc-/ll- classes — never Streamlit globals), exactly as the shipped home does.

3. Suggested order (each its own reviewed slice)

  • S1 — shared theme module: extract the home's CSS tokens into one helper (e.g. app/_ui.py) both home and pages import. No visible change beyond consistency.
  • S2 — page-header helper: adopt on 1 page (Fight Groups) behind its AppTest, then roll out page by page.
  • S3 — Odds review queue: status-cell styling on the existing match table.
  • S4 — context bar: opt-in per page, reusing the global active_slate_id already written by home.

4. Constraints carried over (unchanged)

  • Read-only on load; no INSERT/UPDATE/DELETE on render (docs/DEVELOPMENT_NOTES.md §11).
  • No optimizer run / export build / odds recompute on load — buttons stay explicit.
  • Render existing check status; never re-derive verdicts. No effective_status promotion.
  • Each slice ships with its AppTest; copy/label strings pinned by tests are updated in lock-step.
